# mizzzee-reverse

BLE 情趣设备（`mizzzee_0008`，白牌 `urt-01` 方案模组）的完整协议逆向工程 + PC 控制台。

**本项目是对用户自有设备所做的授权安全研究**，目标是搞清楚这台机器的 BLE 协议到底能控制什么、边界在哪里，并据此实现一个功能完整的 PC 控制端。

---

## 一、最终成果：完整协议规范

逆向的净产出是一份经过实测验证的协议规范。

### 帧格式

```
AA | cmd | len | payload... | checksum
```

- `checksum = (AA + cmd + len + payload 所有字节) & 0xFF`
- 所有多字节字段均为**大端序**，无转义、无分帧、无加密

### 命令集（实测仅 3 个有效）

| cmd | 帧 | 作用 | 应答 |
|---|---|---|---|
| `0x08` | `AA 08 01 <level>` | **强度控制**，level 0–254 | `AA 09 06 <payload> <sum> 00 00 <X> <crc>` |
| `0x04` | `AA 04 01 <0/1>` | 加热开关 | `AA 05 01 <payload> <crc>` |
| `0x06` | `AA 06 01 <n>` / `AA 06 05 <5字节>` | 已实现但**无可观测副作用**（推测为多马达机型兼容指令） | `AA 07 05 <payload> <sum> 00 00 <crc>` |
| 其余 253 个 | — | **未实现**，静默丢弃 | 无 |

### 关键发现

1. **强度真实量程是 0–254，不是 0–100。** 全范围扫描证实 0..254 全部被 ACK 回显，**255 被拒收**。原版 App 的 0-100 滑杆只用到约 39% 量程。
2. **设备会丢帧。** 连续突发下发（实测 66 帧）后 ACK 完全消失。这解释了大量用户反馈的"按太快会没反应"。本项目在协议层强制 180ms 最小发送间隔。
3. **没有机载模式表。** APK 里的 `writeSpecialMode` 有 13 个索引（10 个 `AA 0A 01 01..0A` 模式帧 + 加热开关 + 停止），但本机对 `0x0A` **完全无应答**。
4. **没有 OTA/DFU 通道**，无法通过蓝牙拉取固件。
5. **状态帧** `AA 01 06 <电量> <b1> <b2> 01 <计数器> <crc>` 约 12 秒一条自发上报，第 5 字节是会话命令计数器（非模式位）。

## 二、完整逆向思路（按时间顺序）

### 阶段 0：抓包失败，转向静态分析

最初的计划是抓官方 App 的蓝牙 HCI 日志。两条路都断了：

- Android 开发者选项里的「启用蓝牙 HCI 信息中心」需要**系统级权限**，普通用户点不动
- 手机没有 root，`su` 不可用

**转向点：** 既然拿不到运行时流量，就从 APK 静态分析入手——协议构造逻辑一定在客户端代码里。

### 阶段 1：解包 APK，定位协议代码

App 是 **uni-app** 打包的（`assets/apps/__UNI__E392D13/www/`），核心逻辑在 4MB 的 `app-service.js`。

关键突破是找到**指令构造函数的调用点**：搜 `"aa"` 只找到 4 个硬编码帧，但顺着 `writeSpecialMode` 摸到了完整的指令表：

```js
writeSpecialMode(t){
  const o=["aa0A0101b6","aa0A0102b7","aa0A0103b8","aa0A0104b9","aa0A0105BA",
           "aa0A0106bb","aa0A0107bc","aa060101b2","aa060100b1","aa0a0100b5",
           "aa0A0108bd","aa0A0109be","aa0A010abf"][t];
  return this.writeData(o)
}
```

索引 0–6 和 10–12 共 **10 个模式帧**，7/8 是加热开关，9 是停止。

同时定位到三个核心函数：
- `Ce(cmd, vals)` —— 帧构造
- `nt(码表, 双人选, 马达数, 是否停止)` —— 马达数组
- `Oe(强度, 选中, 马达数, 停止)` —— 强度映射

### 阶段 2：把官方函数抠出来在 Node 里跑（关键一步）

静态读代码容易看错。**最可靠的办法是把官方函数原样抽出来执行**，拿它的真实输出当基准。

`src/proto_extract.js` 做了这件事：用括号深度匹配从 `app-service.js` 里切出 `Ce`/`nt`/`Oe`/`Pe`/`bt` 五个函数，配上桩（stub）后在 Node 里跑：

```js
var h = () => {};
var nr = () => ({ deviceInfo: { motorNum: 1, prefix: "08", isXht: false },
                  deviceArray: [], allFeatList: [] });
```

**实测输出：**

```
Ce("08", [50])              = aa080132e5
Ce("06", [4,6,5])           = aa0603040605c2
nt([4,6,5], [], 1, false)   = [4]          ← motorNum=1 时只取码表首元素
Oe(50, [1], 1, false)       = [50]         ← 0-100 直接映射，无 /4 缩放
```

这一步的价值：**我们的实现与官方逐字节一致**，协议层不存在偏差。后续所有"某功能没反应"的排查都可以排除帧格式问题。

### 阶段 3：BLE 实测，逐个命令验证

有了正确的帧，开始实测。第一轮就发现：

| 官方帧 | 实测结果 |
|---|---|
| `AA 08 01 <level>` | ✅ 立即生效 |
| `AA 04 01 <0/1>` | ✅ 加热 ACK 正常 |
| `AA 06 05 <5字节>` | ⚠️ 有 ACK，**无任何动作** |
| `AA 0A 01 <n>` | ❌ **完全无应答** |

**这是整个逆向最重要的判断：这台机器的固件和 APK 里的指令表不是一套。** APK 要兼容多个机型，`writeSpecialMode` 是给老机型用的；`mizzzee_0008` 这块固件只实现了强度 + 加热。

### 阶段 4：256 个命令字节全扫描

为了确认"只有 3 个命令"不是漏测，做了全扫描：对 `0x00`–`0xFF` 每个命令字节各发 2 种长度，用「有没有 ACK」做客观判据。

```
cmd 0x04  → aa 05 01 ...
cmd 0x06  → aa 07 05 ...
cmd 0x08  → aa 09 06 ...
其余 253 个 → 静默
```

中途 `0x3D`/`0xEF` 出现过"命中"，用单帧触发实验证伪了——那只是约 12 秒一次的周期状态帧碰巧赶到，不是应答。

### 阶段 5：解析 ACK 与状态帧，寻找模式状态位

既然没有机载模式，那 `0x06` 到底做了什么？思路是找**客观反馈通道**。

ACK 结构解析：
```
0x08 → AA 09 06 <payload> <sum> 00 00 <X> <crc>
```

一度以为尾部 `<X>` 是状态位（观察到 `0xB0` / `0x30` 两种值），但实测**强度 0 和强度 90 给出完全相同的值**，判定为滚动计数/校验，不是状态。

状态帧第 5 字节也曾被误判为模式位（观察到 01→05 单调递增），最终确认是**会话命令计数器**。

**两条探针路径都走完后，结论才立得住：设备不提供任何模式状态反馈。**

### 阶段 6：量程标定——最大的实际收获

前面都在找"更多功能"，但真正有价值的发现来自一个简单问题：**强度到底能发到多大？**

全范围扫描 0–255：

```
发送   0 → ACK 回显 [0]
发送 100 → ACK 回显 [100]
发送 200 → ACK 回显 [200]
发送 254 → ACK 回显 [254]
发送 255 → 无应答        ← 被拒收
```

**真实量程 0–254。** 原版 App 的滑杆只到 100，等于放弃了 61% 的量程。这很可能是大量用户觉得"不够猛"的根本原因。

实现上采用了**逻辑强度(0-100) → 物理输出(0-254)** 的映射层：所有波形曲线内部仍按 0-100 设计（节奏形状不变），只在最终输出时缩放。一处改动，全链路生效。

### 阶段 7：帧率保护

第 6 轮多字节测试时，连续发了 66 帧，结果 `0x06` 的 ACK **完全消失**——设备在丢帧。

这正好对上了最早期的用户反馈：「如果按的过快 飞机杯会没反应 切换不了」。根因是固件处理能力有限，不是软件逻辑错。

修法是在协议层强制**两次写入最小间隔 180ms**。这样无论用户怎么点、语音识别多快、AI 多频繁改值，都不会再把设备刷爆。

### 阶段 8：服务端接口探测与登录墙

机型配置（`prefix`、`motorNum`、`modeList`）在服务端：

```
接口根  https://akn.ankeni.net/zqf/api/
免登录  sys/config/getMap、sys/dict/getDictByTypeAndCode、device/rank/*
需登录  device/info/getDeviceLastStatus   ← deviceTypeConfig 在这里
```

服务端有**免 token 白名单**（只有 `player/*` 登录类接口），设备配置接口不在其中。带假 token 同样返回 401。

由于 Node 阶段已证明 `prefix=08`、`motorNum=1` 与实际行为一致，这个缺口不影响结论。入口已做进程序（「配置」按钮），用户自行填入 token 即可，密钥不必经过开发者。

## 三、功能清单

### PC 控制台（`src/mizzzee_gui.py`）

| 页签 | 功能 |
|---|---|
| **技能** | 5 个官方技能 + 9 种软件抽动模式 + 10 个 APK 原生固件模式 + 档位滑杆（0-254） |
| **变频** | 28 种波形（潮汐/心跳/呼吸/雷雨/弹跳球/温泉/渐入…）+ 慢中快三档 + 柔化开关 + BPM 节拍 + 盲盒 + 突袭 |
| **语音** | 声控（麦克风跟随音乐）+ 离线中文关键词识别（vosk）：快点/慢点/停/重点/好爽/加热 |
| **视频** | 加载视频，**动作(帧差) + 声音(RMS) 双通道融合**生成强度曲线；可拖动进度、可全屏、有声音 |
| **AI** | 接入 OpenAI 兼容接口，让 AI 生成节奏剧本；**预生成+缓冲播放**架构隐藏 LLM 延迟 |
| **手动** | 强度滑杆（0-254）+ 加热 + 安全停止 + 运行时长 |

### 关键技术点

**1. 变频引擎** —— 每个波形是一个返回强度列表的函数，每元素 = 250ms（与保活同频）。引擎按累计时间推进，支持非 250ms 倍数步长（如 90 BPM 的 333ms）。

**2. 柔化算法** —— `soften(levels, max_step)` 限速滤波，限制每步变化幅度，去掉生硬跳变。这是舒适度最关键的一项。

**3. 视频音画融合** —— cv2 逐帧缩到 96×54 灰度算帧间绝对差（动作通道）；ffmpeg 抽 16k 单声道算 40ms 窗口 RMS（声音通道）；两条曲线重采样到统一 40ms 网格后按权重加权。四种玩法可实时切换：动作优先/均衡/声音优先/只看声音。

**4. AI 缓冲播放** —— LLM 单次调用 1–3 秒，直接一问一答必然卡顿。所以让 AI 一次返回 10 步 JSON 剧本，本地按毫秒精确播放，缓冲低于 4 秒时后台静默预取下一批。**设备侧指令间隔完全由本地时钟控制，LLM 延迟被缓冲吸收。**

**5. 帧率保护** —— 协议层 180ms 最小间隔，杜绝突发丢帧。

## 四、构建与运行

### 依赖

```bash
pip install PySide6 bleak sounddevice vosk opencv-python-headless imageio-ffmpeg numpy
```

### 运行

```bash
# 设置设备地址（或留空自动扫描名称含 mizzzee 的设备）
export MIZZZEE_ADDR="XX:XX:XX:XX:XX:XX"

# 如需 AI 功能
export AI_API_KEY="your-key"
export AI_BASE_URL="https://your-endpoint/v1"

python src/mizzzee_gui.py
```

### 语音模型（可选）

语音识别需要 vosk 中文小模型（66MB），放在 `model/` 目录：

```
model/vosk-model-small-cn-0.22/
```

下载：<https://alphacephei.com/vosk/models/vosk-model-small-cn-0.22.zip>
缺少模型时语音按钮会提示「模型未找到」，其他功能不受影响。

### 打包

```bash
pyinstaller --onefile --windowed --name MizzzeeControl \
  --collect-all bleak --collect-all winrt --collect-all sounddevice \
  --collect-all vosk --collect-all cv2 --collect-all imageio_ffmpeg \
  --collect-submodules PySide6.QtMultimedia \
  --hidden-import config_tool \
  src/mizzzee_gui.py src/config_tool.py
```

约 176MB（含 ffmpeg 与 opencv）。

## 七、结论与遗留问题

### 已确认

- 协议层实现与官方 App 逐字节一致
- 设备为单马达，固件仅实现「强度(0-254) + 加热(0x04)」
- 无机载模式表、无 OTA 通道、无隐藏 GATT 服务

### 未解决（需实物配合）

1. `AA 06 01 <n>` 被设备接受但不回显任何状态，**可能驱动第二个马达**（如吸吮/伸缩）。这种效果无法远程观测，需人在设备旁逐条测试——`src/mode_probe.py` 即为此事而写。
2. USB-C 口是否为纯充电口（无数据线），需插线后对比系统 PnP 设备。
3. 「边充边用」取决于硬件电源路径：若固件在充电时拒绝指令则可绕，若硬件切断马达供电则软件无解。
